# step1. カメラとライトをシェーダーへ渡す

**ゴール**: 氷のシェーダーに書いたカメラとライトの数字 (ハードコード) を無くし、 C++ の値を毎フレーム受け取る。
後の段 (レイマーチ・屈折・影) は、 カメラの位置と行列、 ライトの向きを何度も使う。 ここを先に直しておく。

計算の解説: [`docs/04-camera-light.md`](../04-camera-light.md)。 見本: `src/engine/SceneConstants.h`, `src/engine/shaders/SceneConstants.hlsli`, `src/ice/IceImplement.cpp` (`createRootSignature`, `draw3D`)。

---

## 1. 今のシェーダーが何を受け取っているか調べる

1. プリミティブを描いている自分のシェーダーを開き、 `cbuffer` (または `ConstantBuffer<…>`) の宣言をすべて書き出す。
   - 名前、 レジスター (`b0` など)、 中の変数 (行列・位置・色)
2. 頂点シェーダーで、 頂点を画面へ移している行 (`mul(…)`) を探す。 そこで使っている行列が **カメラの行列**。 これはもう C++ から届いている。
3. `#include` を見る。 共通の `.hlsli` に、 エンジンのシーンやフレームの定数が書かれていることが多い。

> 行列は届いているのにライトだけハードコード、 ということはよくある。 行列が来ている定数バッファの近くに、 ライトの値も入っていないか探す。

## 2. C++ でその番号に何を結び付けているか調べる

[`docs/04-camera-light.md`](../04-camera-light.md) §5.2 の言葉で検索する。 たどる順:

1. ルートシグネチャを作っている所 (`D3D12_ROOT_PARAMETER`, `CreateRootSignature`) → 何番の引数が何のレジスターか。
2. 描く前にその引数を設定している所 (`SetGraphicsRootConstantBufferView` など) → どのバッファを渡しているか。
3. そのバッファに書いている所 (`Map`, `memcpy`) → **何の値を、 どのクラスから取って書いているか**。 ここにカメラとライトの持ち主がいる。

## 3. RenderDoc で中身を見る (いちばん確実)

1. RenderDoc (または PIX) からアプリを起動し、 プリミティブが映ったフレームを取り込む。
2. プリミティブを描く命令 (`DrawIndexedInstanced`) を選ぶ。
3. Pipeline State → 頂点シェーダー / ピクセルシェーダー → Constant Buffers を開く。
4. 行列らしい 4 × 4 の値、 向きらしい長さ 1 の値を探す。 カメラを動かして取り込み直し、 変わる値と変わらない値を見比べる。

ここで **「何番のレジスターに、 どの値が、 どの並びで入っているか」** を書き留める。

## 4. 氷のシェーダーで同じ値を読む

### 4.1 エンジンにシーンの定数がある場合 (多くのエンジン)

1. 氷のシェーダーで、 既存のシェーダーと **同じ `.hlsli` を `#include`** する (宣言を自分で書き写さない。 並びがずれる元)。
2. `IceImplement` のルートシグネチャに、 同じレジスターの引数を足す (見本: `IceImplement::createRootSignature` の `kRootScene`)。
3. `draw3D` で、 エンジンからその定数バッファの GPU のアドレスを受け取り、 結び付ける。

```cpp
// 見本 (IceImplement::draw3D)
commandList->SetGraphicsRootConstantBufferView(kRootScene, context.sceneConstants);
```

エンジンがアドレスを渡してくれない場合は、 「今のフレームのシーンの定数バッファ」 を返す関数を探す (Renderer やシーンのクラスにあることが多い)。

### 4.2 エンジンに無い・使えない場合

`IceImplement` が自分の定数バッファを持つ。

1. アップロードヒープに 256 バイトの倍数の大きさのバッファを作り、 `Map` したままにする (見本: `Renderer::createSceneConstantBuffer`)。
2. 毎フレーム `draw3D` の最初で、 エンジンのカメラとライトのクラスから値を取って書く。
   - カメラ: ビュー行列 × 射影行列、 カメラの位置
   - ライト: 向き、 色 × 強さ
3. 行列はシェーダーの読み方に合わせて転置する (下の 「つまずきやすい所」)。
4. ルートシグネチャの引数に結び付ける。

> GPU が前のフレームを描き終える前に次のフレームを作るエンジンでは、 1 つのバッファを毎フレーム書き換えると、 GPU が読んでいる途中の値が変わってしまう。 フレームの数だけバッファを持つか、 エンジンの 「毎フレーム使い捨ての定数バッファ」 の仕組みを使う。

## 5. ハードコードを置き換える

1. 氷のシェーダーの数字 (ライトの向き・色、 カメラの位置) を、 定数の変数に置き換える。
2. 1 か所 (`.hlsli`) にまとめ、 関数で読む形にしておくと、 後で取り方を変えるときに 1 か所で済む。

```hlsl
// 見本 (Environment.hlsli)
float3 SunColor()     { return LightColor; }
float3 SunDirection() { return LightDirection; }
```

3. **ライトの向きの約束** を確かめる。 このリポジトリは 「面から光源へ向かう向き」。 エンジンが 「光が進む向き」 なら、 符号を反転して使う。

## 確かめ方

- [ ] シェーダーに、 ライトとカメラの数字が残っていない (検索して確かめる)
- [ ] エンジンでライトの向きを変えると、 氷の照らされ方が変わる。 周りの物と同じ側が明るい
- [ ] カメラを動かしても、 氷と周りの物がずれない
- [ ] RenderDoc で、 氷を描く命令の定数バッファに、 正しい値が入っている

## つまずきやすい所

| 症状 | 原因 |
| --- | --- |
| 何も映らない・画面いっぱいに伸びる | 行列の転置か掛ける順が逆 (`mul(v, M)` と `mul(M, v)`)。 既存のシェーダーと同じ書き方にする |
| 照らされる面が逆 | ライトの向きの約束が逆 |
| 値が 1 つずれて入る | `float3` の後の 16 バイトの区切り (C++ 側に詰め物が無い) |
| 1 フレーム遅れて動く | 描く命令の後で定数を書いている |
| ときどきちらつく | GPU が読んでいる途中のバッファを書き換えている |
